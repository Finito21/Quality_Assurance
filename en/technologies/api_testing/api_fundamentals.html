    API Fundamentals

    1. API¶

    API - to interfejs programowania aplikacji. To zestaw protokołów i narzędzi umożliwiających komunikację pomiędzy składnikami oprogramowania i aplikacjami sieciowymi oraz wymianę danych między oddzielnymi systemami. Api dostarcza interfejsu, który określa jak programy mogą się ze sobą komunikować, jakie dane można wymieniać i jak korzystać z udostępnionych funkcji. Łatwo umożliwiają integracje, rozszerzalność oraz gotowe funkcje dzięki czemu nie trzeba ich pisać od nowa. Umożliwia pobranie danych np. bazy danych czy serwisów.

    1.1. Cykl życia API¶

    Cykl życia API - to proces obejmujący wszystkie etapy tworzenia i utrzymania API, od projektowania i implementacji, przez testowanie oraz wdrożenie, aż po monitorowanie, rozwój i utrzymanie kolejnych wersji interfejsu.

    1.2. Klient API¶

    Klient API - to narzędzie lub aplikacja umożliwiająca wysyłanie żądań do API oraz odbieranie odpowiedzi z serwera. Klient API ułatwia testowanie, debugowanie oraz analizowanie działania interfejsów API. Np. Postman i Insomnia.

    1.3. Dokumentacja API¶

    Dokumentacja API - zbiór informacji opisujących sposób korzystania z API oraz jego integracji z innymi systemami. Zawiera m.in. dostępne endpointy, metody, parametry, sposób autoryzacji oraz przykłady zapytań i odpowiedzi.

    1.4. Jak działa API?¶

    API (Application Programming Interface) umożliwia komunikację między aplikacjami, systemami lub urządzeniami poprzez wymianę danych. Działa na zasadzie modelu żądanie → odpowiedź (request → response).

    1. Klient API wysyła żądanie

    Proces rozpoczyna klient API, np. aplikacja mobilna, strona internetowa lub inny system. Żądanie może zostać wywołane przez działanie użytkownika, np. kliknięcie przycisku „Zaloguj”, wyszukanie produktu lub pobranie danych.

    2. Żądanie API (API Request)

    Żądanie wysyłane do serwera API zazwyczaj zawiera:

    • Endpoint - adres URL wskazujący konkretny zasób lub funkcję API, np. /users lub /orders.
    • Metodę HTTP - określa rodzaj operacji
    • Parametry - dodatkowe informacje przekazywane do API, np. identyfikator użytkownika lub filtr wyszukiwania.
    • Nagłówki (Headers) - dane techniczne, np. typ danych lub token autoryzacyjny.
    • Body (treść żądania) - dane przesyłane do serwera, np. formularz rejestracyjny w formacie JSON.

    3. Serwer API przetwarza żądanie

    Serwer API odbiera żądanie i wykonuje odpowiednie operacje, takie jak:

    • weryfikacja użytkownika,
    • walidacja danych,
    • komunikacja z bazą danych,
    • przetworzenie logiki biznesowej,
    • przygotowanie odpowiedzi.

    4. API zwraca odpowiedź

    Po przetworzeniu żądania serwer odsyła odpowiedź do klienta. Odpowiedź zwykle zawiera:

    • Kod statusu HTTP - informację o wyniku operacji,
    • Response Headers - dodatkowe informacje techniczne.
    • Response Body - właściwe dane lub komunikat błędu.

    1.5. Typy API¶

    • Private API - nazywane również Internal API, to interfejsy dostępne wyłącznie wewnątrz organizacji. Służą do komunikacji pomiędzy wewnętrznymi systemami, aplikacjami lub usługami firmy.

    • Public API - interfejsy udostępniane zewnętrznym użytkownikom oraz developerom. Umożliwiają integrację aplikacji z usługami lub funkcjonalnościami dostępnymi publicznie.

    • Partner API - interfejsy udostępniane wybranym partnerom biznesowym. Dostęp do nich jest ograniczony i wymaga odpowiedniej autoryzacji lub umowy pomiędzy organizacjami.

    2. Rodzaje API¶

    Istnieje wiele rodzajów API różniących się sposobem komunikacji, strukturą danych, wydajnością oraz zastosowaniem. Wybór odpowiedniego typu API zależy między innymi od wymagań projektu, architektury systemu oraz potrzeb biznesowych.

    2.1. REST API¶

    • REST API to interfejs programistyczny oparty na architekturze REST (Representational State Transfer), wykorzystywany do komunikacji pomiędzy klientem a serwerem przy użyciu protokołu HTTP.
    • Komunikacja w REST API odbywa się najczęściej z wykorzystaniem formatów JSON lub XML, jednak JSON jest obecnie najpopularniejszym standardem.
    • REST API wykorzystuje standardowe metody HTTP do wykonywania operacji na zasobach, takie jak GET, POST, PUT, PATCH oraz DELETE.
    • Każdy zasób w REST API posiada unikalny adres URL zwany endpointem.
    • REST API jest bezstanowe (stateless), co oznacza, że każde żądanie zawiera wszystkie informacje potrzebne do jego obsługi, a serwer nie przechowuje informacji o poprzednich żądaniach klienta.
    • Dane przesyłane pomiędzy klientem a serwerem mogą znajdować się w nagłówkach HTTP, parametrach zapytania, ścieżce URL lub body requestu.
    • REST API jest często wykorzystywane w aplikacjach webowych, mobilnych oraz systemach opartych na mikroserwisach.
    • Dzięki swojej prostocie, wydajności oraz łatwej integracji REST API jest obecnie najpopularniejszym typem API.

    2.2. SOAP API¶

    • SOAP API to interfejs oparty na protokole SOAP (Simple Object Access Protocol), wykorzystywany do wymiany danych pomiędzy aplikacjami.
    • SOAP API korzysta głównie z formatu XML do przesyłania wiadomości pomiędzy klientem a serwerem.
    • Komunikacja w SOAP opiera się na ściśle określonych zasadach oraz standardach definiujących strukturę wiadomości i sposób wymiany danych.
    • SOAP może działać z wykorzystaniem różnych protokołów transportowych, takich jak HTTP, SMTP czy FTP.
    • Każda wiadomość SOAP posiada określoną strukturę XML zawierającą informacje o żądaniu, odpowiedzi oraz dodatkowych metadanych.
    • SOAP wykorzystuje WSDL (Web Services Description Language), czyli dokument opisujący dostępne operacje API, parametry oraz typy danych.
    • Dzięki ścisłej standaryzacji SOAP API zapewnia wysoki poziom bezpieczeństwa, niezawodności oraz integralności danych.
    • SOAP API jest często wykorzystywane w systemach enterprise, bankowości, systemach finansowych oraz integracjach wymagających wysokiego poziomu bezpieczeństwa.
    • W porównaniu do REST API SOAP jest bardziej rozbudowany, bardziej restrykcyjny oraz zwykle trudniejszy w implementacji i utrzymaniu.

    2.3. GraphQL¶

    • GraphQL to język zapytań do API opracowany przez firmę Facebook, umożliwiający klientowi pobieranie dokładnie tych danych, które są potrzebne.
    • GraphQL wykorzystuje jeden endpoint API, przez który obsługiwane są wszystkie zapytania i operacje.
    • Klient sam określa strukturę odpowiedzi oraz wybiera pola, które mają zostać zwrócone przez serwer.
    • Dzięki możliwości pobierania konkretnych danych GraphQL pomaga ograniczyć problem nadmiarowych danych (overfetching) oraz brakujących danych (underfetching).
    • GraphQL obsługuje operacje takie jak Query do pobierania danych, Mutation do modyfikacji danych oraz Subscription do obsługi komunikacji w czasie rzeczywistym.
    • Komunikacja w GraphQL odbywa się najczęściej z wykorzystaniem protokołu HTTP oraz formatu JSON.
    • GraphQL jest często wykorzystywany w nowoczesnych aplikacjach webowych i mobilnych wymagających elastycznego pobierania danych.
    • Dzięki jednej strukturze endpointów GraphQL może uprościć komunikację pomiędzy frontendem a backendem.
    • W porównaniu do REST API GraphQL zapewnia większą elastyczność w pobieraniu danych, jednak może być bardziej złożony w implementacji oraz monitorowaniu.

    2.4. gRPC¶

    • gRPC to nowoczesny framework komunikacji opracowany przez Google, oparty na architekturze Remote Procedure Call (RPC).
    • gRPC umożliwia wywoływanie metod na serwerze podobnie jak lokalnych funkcji lub metod w aplikacji.
    • Komunikacja w gRPC wykorzystuje protokół HTTP/2, który zapewnia wysoką wydajność oraz szybszą transmisję danych.
    • Dane w gRPC są przesyłane w formacie Protocol Buffers (Protobuf), który jest bardziej wydajny i lżejszy od JSON lub XML.
    • gRPC wspiera komunikację synchroniczną, asynchroniczną oraz streaming danych pomiędzy klientem a serwerem.
    • Dzięki wykorzystaniu HTTP/2 gRPC obsługuje między innymi multiplexing, kompresję nagłówków oraz dwukierunkowy streaming.
    • gRPC jest często wykorzystywane w architekturze mikroserwisów oraz systemach wymagających wysokiej wydajności i niskich opóźnień.
    • Framework umożliwia automatyczne generowanie kodu klienta i serwera dla wielu języków programowania.
    • W porównaniu do REST API gRPC oferuje wyższą wydajność oraz szybszą komunikację, jednak jest mniej czytelny dla człowieka i trudniejszy do testowania w tradycyjnych narzędziach HTTP.

    3. HTTP¶

    HTTP (HyperText Transfer Protocol) to podstawowy protokół komunikacyjny wykorzystywany w sieci WWW do wymiany danych pomiędzy klientem a serwerem. HTTP działa w modelu klient–serwer oraz opiera się na mechanizmie żądanie–odpowiedź (request–response).

    Klient, na przykład przeglądarka internetowa, aplikacja mobilna lub narzędzie do testowania API, wysyła żądanie HTTP do serwera. Następnie serwer przetwarza żądanie i zwraca odpowiedź zawierającą informacje o wyniku operacji.

    Żądanie HTTP może zawierać:

    • metodę HTTP określającą rodzaj wykonywanej operacji,
    • adres URL zasobu,
    • nagłówki HTTP (headers),
    • parametry zapytania,
    • opcjonalne body requestu zawierające dane przesyłane do serwera.

    Odpowiedź HTTP zwracana przez serwer może zawierać:

    • kod odpowiedzi HTTP informujący o rezultacie operacji,
    • nagłówki odpowiedzi,
    • opcjonalne body response zawierające dane zwrócone przez serwer.

    HTTP jest protokołem bezstanowym (stateless), co oznacza, że każde żądanie HTTP jest przetwarzane niezależnie od poprzednich żądań.

    Serwer nie przechowuje automatycznie informacji o stanie użytkownika pomiędzy requestami. Aby utrzymać sesję lub rozpoznać użytkownika, wykorzystywane są dodatkowe mechanizmy, takie jak cookies, session ID lub tokeny autoryzacyjne.

    3.1. Metody HTTP¶

    Metody HTTP określają rodzaj operacji wykonywanej na zasobie znajdującym się na serwerze. Każda metoda posiada określone przeznaczenie oraz sposób działania.

    1. GET

    Metoda GET służy do pobierania danych z serwera. Jest jedną z najczęściej wykorzystywanych metod HTTP i nie powinna modyfikować danych znajdujących się po stronie aplikacji.

    Dane w metodzie GET najczęściej przekazywane są:

    • w parametrach query,
    • w ścieżce URL,
    • w nagłówkach HTTP.

    Metoda GET jest uznawana za bezpieczną (safe) i idempotentną (idempotent), co oznacza że wielokrotne wykonanie tego samego żądania GET nie powinno zmieniać stanu systemu.

    Typowe problemy związane z metodą GET:

    • zwracanie nieaktualnych danych przez cache,
    • przesyłanie wrażliwych danych w URL,
    • zbyt długa długość adresu URL,
    • niepoprawna obsługa parametrów query,
    • modyfikowanie danych przez endpoint GET, co jest niezgodne ze standardem HTTP.

    2. POST

    Metoda POST służy do przesyłania danych do serwera w celu utworzenia nowego zasobu lub wykonania określonej operacji biznesowej.

    Dane najczęściej przesyłane są:

    • w body requestu,
    • w formacie JSON lub XML,
    • wraz z nagłówkami określającymi typ danych.

    POST nie jest metodą idempotentną, co oznacza, że wielokrotne wysłanie tego samego requestu może prowadzić do utworzenia wielu zasobów lub wielokrotnego wykonania operacji.

    Metoda POST jest często wykorzystywana do:

    • tworzenia nowych rekordów,
    • logowania użytkownika,
    • przesyłania formularzy,
    • uploadu plików,
    • wykonywania operacji biznesowych.

    Typowe problemy związane z metodą POST:

    • brak walidacji danych wejściowych,
    • możliwość duplikacji danych,
    • błędna obsługa body requestu,
    • niepoprawne statusy odpowiedzi,
    • przesyłanie zbyt dużych payloadów.

    3. PUT

    Metoda PUT służy do aktualizacji istniejącego zasobu lub całkowitego nadpisania jego danych.

    PUT zazwyczaj wymaga przesłania pełnej reprezentacji aktualizowanego obiektu. Jeśli część pól nie zostanie przesłana, mogą zostać nadpisane pustymi wartościami lub usunięte.

    Metoda PUT jest idempotentna, co oznacza, że wielokrotne wykonanie tego samego requestu powinno prowadzić do tego samego rezultatu.

    PUT jest często wykorzystywany do:

    • pełnej aktualizacji danych użytkownika,
    • aktualizacji konfiguracji,
    • nadpisywania zasobów.

    Typowe problemy związane z metodą PUT:

    • przypadkowe nadpisanie danych,
    • utrata pól niewysłanych w request body,
    • błędna walidacja danych,
    • brak kontroli wersji danych,
    • konflikty podczas równoczesnej edycji zasobów.

    4. PATCH

    Metoda PATCH służy do częściowej aktualizacji istniejącego zasobu. Pozwala zmodyfikować wybrane pola bez konieczności przesyłania całego obiektu.

    PATCH jest bardziej elastyczny niż PUT i często wykorzystywany w nowoczesnych API do wykonywania niewielkich zmian w danych.

    W zależności od implementacji PATCH może być:

    • idempotentny,
    • częściowo idempotentny,
    • nieidempotentny.

    PATCH najczęściej wykorzystywany jest do:

    • zmiany pojedynczych pól,
    • aktualizacji statusów,
    • częściowej edycji danych użytkownika.

    Typowe problemy związane z metodą PATCH:

    • niepoprawna aktualizacja części danych,
    • brak walidacji zmienianych pól,
    • niespójność danych,
    • problemy z równoczesną edycją rekordów,
    • trudniejsza implementacja logiki aktualizacji.

    5. DELETE

    Metoda DELETE służy do usuwania zasobu znajdującego się na serwerze.

    DELETE jest metodą idempotentną, ponieważ wielokrotne usunięcie tego samego zasobu powinno prowadzić do tego samego rezultatu końcowego.

    Usunięcie zasobu może być:

    • fizyczne (hard delete),
    • logiczne (soft delete).

    W przypadku soft delete rekord pozostaje w bazie danych, ale jest oznaczony jako usunięty.

    Typowe problemy związane z metodą DELETE:

    • brak odpowiednich uprawnień,
    • przypadkowe usuwanie danych,
    • brak obsługi zależności pomiędzy rekordami,
    • problemy z cache,
    • możliwość usunięcia zasobów używanych przez inne systemy.

    3.2. Kody odpowiedzi HTTP¶

    Kody odpowiedzi HTTP (HTTP Status Codes) to komunikaty zwracane przez serwer informujące o rezultacie wykonania żądania HTTP.

    3.2.1. Kody 2xx¶

    Kody z grupy 2xx oznaczają, że żądanie zostało poprawnie przetworzone przez serwer i zakończyło się sukcesem.

    Najczęściej spotykane kody:

    • 200 OK – żądanie zostało wykonane poprawnie,
    • 201 Created – zasób został pomyślnie utworzony,
    • 204 No Content – operacja zakończyła się sukcesem, ale odpowiedź nie zawiera danych.

    Typowe problemy:

    • zwracanie kodu sukcesu mimo wystąpienia błędu,
    • niepoprawny status dla danej operacji,
    • brak zgodności statusów z dokumentacją API.

    3.2.2. Kody 3xx¶

    Kody z grupy 3xx informują o przekierowaniu żądania do innego zasobu lub adresu URL.

    Najczęściej spotykane kody:

    • 300 Multiple Choices – zasób posiada kilka możliwych odpowiedzi lub wersji, a klient może wybrać odpowiednią opcję.
    • 301 Moved Permanently – zasób został trwale przeniesiony,
    • 302 Found – tymczasowe przekierowanie,
    • 304 Not Modified – zasób nie został zmodyfikowany i może zostać pobrany z cache.

    Kody 3xx wykorzystywane są głównie:

    • przy przekierowaniach URL,
    • w mechanizmach cache,
    • podczas migracji endpointów API.

    Typowe problemy:

    • błędne przekierowania,
    • pętle redirectów,
    • niepoprawna konfiguracja cache,
    • przekierowania do nieistniejących zasobów.

    3.2.3. Kody 4xx¶

    Kody z grupy 4xx oznaczają błędy po stronie klienta. Serwer otrzymał żądanie, ale nie może go poprawnie przetworzyć z powodu problemu w requestcie.

    Najczęściej spotykane kody:

    • 400 Bad Request – niepoprawne żądanie,
    • 401 Unauthorized – brak uwierzytelnienia,
    • 403 Forbidden – brak uprawnień,
    • 404 Not Found – zasób nie istnieje,
    • 405 Method Not Allowed – metoda HTTP nie jest dozwolona,
    • 429 Too Many Requests – przekroczono limit żądań.
    - `418 I'm a teapot` – jestem czajnikiem, a nie ekspresem do kawy :)

    Kody 4xx najczęściej pojawiają się w przypadku:

    • błędnych danych wejściowych,
    • problemów z autoryzacją,
    • niepoprawnych endpointów,
    • błędnych parametrów requestu.

    Typowe problemy:

    • nieczytelne komunikaty błędów,
    • zwracanie niewłaściwych statusów,
    • brak walidacji danych,
    • ujawnianie zbyt wielu informacji o systemie.

    3.2.4. Kody 5xx¶

    Kody z grupy 5xx oznaczają błędy po stronie serwera. Żądanie zostało poprawnie wysłane przez klienta, jednak serwer nie był w stanie go obsłużyć.

    Najczęściej spotykane kody:

    • 500 Internal Server Error – wewnętrzny błąd serwera,
    • 501 Not Implemented – serwer nie obsługuje funkcjonalności wymaganej do wykonania żądania lub dana metoda HTTP nie została zaimplementowana.
    • 502 Bad Gateway – niepoprawna odpowiedź z innego serwera,
    • 503 Service Unavailable – usługa chwilowo niedostępna,
    • 504 Gateway Timeout – przekroczono czas oczekiwania na odpowiedź.

    Kody 5xx mogą występować z powodu:

    • błędów aplikacji backendowej,
    • problemów z bazą danych,
    • przeciążenia serwera,
    • błędów integracji pomiędzy systemami,
    • problemów infrastrukturalnych.

    Typowe problemy:

    • niestabilność aplikacji,
    • timeouty,
    • przeciążenie systemu,
    • brak odpowiedniej obsługi wyjątków,
    • niewystarczające logowanie błędów.

    3.3. Nagłówki HTTP¶

    Nagłówki HTTP (HTTP Headers) to dodatkowe informacje przesyłane pomiędzy klientem a serwerem w żądaniach oraz odpowiedziach HTTP. Pozwalają określić sposób komunikacji, typ przesyłanych danych, mechanizmy autoryzacji, cache, bezpieczeństwo oraz wiele innych parametrów związanych z obsługą requestów i response'ów.

    Nagłówki przesyłane są w postaci pary klucz: wartość.

    Przykład: 

    Content-Type: application/json
Authorization: Bearer token

    Nagłówki HTTP mogą występować zarówno:

    • w requestach wysyłanych przez klienta,
    • w odpowiedziach zwracanych przez serwer.

    3.3.1. Najczęściej używane nagłówki HTTP¶

    1. Content-Type

    Nagłówek Content-Type określa typ danych przesyłanych w request body lub response body.

    Najczęściej spotykane wartości:

    • application/json
    • application/xml
    • text/html
    • multipart/form-data

    Niepoprawny Content-Type może powodować:

    • błędne parsowanie danych,
    • problemy z walidacją requestu,
    • błędy komunikacji pomiędzy systemami.

    2. Accept

    Nagłówek Accept informuje serwer, jaki format odpowiedzi akceptuje klient.

    Przykład: 

    Accept: application/json

    Jeśli serwer nie obsługuje wskazanego formatu, może zwrócić: 

    406 Not Acceptable

    3. Authorization

    Nagłówek Authorization służy do przesyłania danych uwierzytelniających użytkownika lub aplikacji.

    Najczęściej wykorzystywane mechanizmy:

    • Bearer Token,
    • Basic Auth,
    • API Key,
    • JWT.

    Przykład: 

    Authorization: Bearer eyJhbGci...

    Typowe problemy:

    • wygasłe tokeny,
    • brak nagłówka autoryzacji,
    • niepoprawny format tokena,
    • wycieki danych uwierzytelniających.

    4. User-Agent

    Nagłówek User-Agent identyfikuje klienta wysyłającego żądanie, np. przeglądarkę, aplikację mobilną lub narzędzie testowe.

    Przykładowe wartości:

    • Chrome,
    • Firefox,
    • PostmanRuntime,
    • curl.

    Niektóre systemy wykorzystują User-Agent do:

    • filtrowania ruchu,
    • blokowania botów,
    • analizy statystyk,
    • personalizacji odpowiedzi.

    Ciekawostka:

    Nagłówek User-Agent może być łatwo modyfikowany, dlatego nie powinien być traktowany jako bezpieczny mechanizm identyfikacji użytkownika.

    5. Host

    Nagłówek Host określa adres domeny serwera, do którego wysyłane jest żądanie.

    Przykład: 

    Host: api.example.com

    Nagłówek ten jest wymagany w HTTP/1.1 i pozwala obsługiwać wiele domen na jednym serwerze.

    6. Cookie

    Nagłówek Cookie służy do przesyłania danych sesji pomiędzy klientem a serwerem.

    Cookies często wykorzystywane są do:

    • utrzymywania sesji użytkownika,
    • przechowywania tokenów,
    • zapamiętywania ustawień aplikacji.

    Typowe problemy:

    • wyciek cookies,
    • brak flag bezpieczeństwa,
    • przechowywanie wrażliwych danych po stronie klienta.

    7. Set-Cookie

    Nagłówek Set-Cookie pozwala serwerowi zapisać cookie w przeglądarce użytkownika.

    Może zawierać dodatkowe flagi bezpieczeństwa:

    • HttpOnly,
    • Secure,
    • SameSite.

    Brak odpowiedniej konfiguracji może prowadzić do:

    • przejęcia sesji,
    • ataków XSS,
    • problemów z bezpieczeństwem aplikacji.

    8. Cache-Control

    Nagłówek Cache-Control określa sposób cache’owania odpowiedzi HTTP.

    Pozwala kontrolować:

    • czas przechowywania danych,
    • możliwość wykorzystania cache,
    • odświeżanie zasobów.

    Niepoprawna konfiguracja cache może powodować:

    • zwracanie nieaktualnych danych,
    • problemy z synchronizacją,
    • błędne działanie aplikacji.

    9. Origin

    Nagłówek Origin określa źródło żądania wysyłanego z przeglądarki.

    Jest wykorzystywany głównie przez mechanizm CORS do kontroli dostępu między domenami.

    Przykład: 

    Origin: https://example.com

    10. Referer

    Nagłówek Referer informuje, z jakiej strony użytkownik przeszedł do aktualnego zasobu.

    Może być wykorzystywany do:

    • analityki,
    • śledzenia ruchu,
    • zabezpieczeń.

    Ciekawostka:

    W nazwie nagłówka występuje literówka (Referer zamiast Referrer), która została zachowana historycznie w standardzie HTTP.

    3.3.2. Znaczenie nagłówków HTTP w testowaniu API¶

    Podczas testowania API nagłówki HTTP są niezwykle istotne, ponieważ wpływają na:

    • autoryzację użytkownika,
    • poprawność komunikacji,
    • bezpieczeństwo aplikacji,
    • cache danych,
    • wersjonowanie API,
    • format przesyłanych danych.

    Niepoprawne nagłówki mogą prowadzić do:

    • błędów autoryzacji,
    • problemów z integracją,
    • błędnego parsowania danych,
    • podatności bezpieczeństwa,
    • niepoprawnego działania aplikacji.

    3.3.3. Ciekawostki dotyczące nagłówków HTTP¶

    • Nagłówki HTTP nie rozróżniają wielkości liter (Content-Type i content-type są traktowane identycznie).
    • W HTTP/2 nagłówki są kompresowane, co poprawia wydajność komunikacji.
    • Niektóre serwery oraz firewalle blokują requesty zawierające podejrzane lub niestandardowe nagłówki.
    • Zbyt duża liczba nagłówków lub bardzo duże wartości mogą powodować błędy typu: 
      http
431 Request Header Fields Too Large
    • Wiele podatności bezpieczeństwa związanych z API wynika z niepoprawnej konfiguracji nagłówków HTTP.

    4. Autoryzacja i uwierzytelnianie¶

    Autoryzacja i uwierzytelnianie są mechanizmami bezpieczeństwa wykorzystywanymi do kontrolowania dostępu do API oraz zasobów systemu.

    Uwierzytelnianie (authentication) odpowiada za potwierdzenie tożsamości użytkownika lub aplikacji, natomiast autoryzacja (authorization) określa, do jakich zasobów i operacji użytkownik posiada dostęp.

    W API najczęściej wykorzystywane są mechanizmy oparte na tokenach, kluczach API oraz standardach autoryzacji takich jak OAuth 2.0.

    4.1. Bearer Token¶

    Bearer Token to jeden z najpopularniejszych sposobów autoryzacji w API. Mechanizm polega na przesyłaniu tokena dostępowego w nagłówku Authorization.

    Przykład: 

    Authorization: Bearer token

    Bearer Token często wykorzystywany jest:

    • w REST API,
    • aplikacjach webowych,
    • aplikacjach mobilnych,
    • systemach opartych na JWT.

    Najważniejsze cechy:

    • token potwierdza tożsamość użytkownika lub aplikacji,
    • token posiada określony czas ważności,
    • serwer weryfikuje poprawność tokena przy każdym requestcie.

    Typowe problemy:

    • wygaśnięcie tokena,
    • wyciek tokenów,
    • brak odpowiedniej ochrony tokenów,
    • przechowywanie tokenów w niebezpiecznych miejscach.

    4.2. Basic Auth¶

    Basic Auth to prosty mechanizm uwierzytelniania oparty na loginie i haśle przesyłanym w nagłówku Authorization.

    Dane użytkownika kodowane są przy użyciu Base64.

    Przykład: 

    Authorization: Basic base64(login:password)

    Najważniejsze cechy:

    • prostota implementacji,
    • łatwa konfiguracja,
    • szerokie wsparcie w narzędziach HTTP.

    Typowe problemy:

    • brak szyfrowania danych,
    • możliwość przechwycenia loginu i hasła,
    • niskie bezpieczeństwo bez HTTPS,
    • przesyłanie danych uwierzytelniających przy każdym requestcie.

    Basic Auth obecnie stosowany jest głównie:

    • w środowiskach testowych,
    • prostych integracjach,
    • systemach wewnętrznych.

    4.3. OAuth 2.0¶

    OAuth 2.0 to standard autoryzacji umożliwiający aplikacjom uzyskanie ograniczonego dostępu do zasobów użytkownika bez konieczności przekazywania hasła.

    OAuth 2.0 wykorzystywany jest między innymi przez:

    • Google,
    • Facebook,
    • GitHub,
    • Microsoft.

    Najważniejsze elementy OAuth 2.0:

    • Access Token,
    • Refresh Token,
    • Authorization Server,
    • Resource Server.

    Najważniejsze cechy:

    • wysoki poziom bezpieczeństwa,
    • możliwość delegowania dostępu,
    • kontrola zakresu uprawnień (scopes),
    • obsługa logowania zewnętrznego.

    Typowe problemy:

    • błędna konfiguracja flow autoryzacji,
    • wyciek tokenów,
    • niewłaściwe zarządzanie refresh tokenami,
    • zbyt szerokie uprawnienia.

    OAuth 2.0 jest obecnie jednym z najczęściej wykorzystywanych standardów autoryzacji w nowoczesnych aplikacjach.

    4.4. Klucze API¶

    Klucze API (API Keys) to unikalne identyfikatory wykorzystywane do autoryzacji aplikacji korzystających z API.

    Klucze API pozwalają:

    • identyfikować klienta API,
    • monitorować wykorzystanie API,
    • ograniczać dostęp do wybranych zasobów,
    • kontrolować limity requestów.

    Klucze API są często wykorzystywane w:

    • publicznych API,
    • integracjach systemowych,
    • usługach SaaS,
    • platformach chmurowych.

    Najczęstsze problemy:

    • publikowanie kluczy w repozytoriach Git,
    • brak rotacji kluczy,
    • brak ograniczeń dostępu,
    • wyciek danych uwierzytelniających.

    5. Testowanie API¶

    Testowanie API potwierdza, że działa ono zgodnie z oczekiwaniami. Przeprowadza się je w celu zapewnienia niezawodnosci funkcjonalności, bezpieczeństwa i wydajności. Testy mogą być uruchamiane ręcznie lub być zautomatyzowane.

    API-first - strategia traktująca API jako najwyzszy priorytet. Aplikacje są konceptualizowane i tworzone jako zbiór usług wewnętrznych i zewnętrznych dostarczanych za pośrednictwem API. Umozliwia ciągłą weryfikacje jakości, kondycji i wydajności endpointów.

    5.1. Rodzaje testów API¶

    Istnieje wiele sposobów testowania API, a każdy z nich służy innemu celowi. W praktyce zespoły często łączą różne podejścia, aby stworzyć skuteczną strategię testowania.

    1. Testy kontraktowe (Contract Testing)

    Testy kontraktowe sprawdzają, czy API działa zgodnie z ustalonym kontraktem, czyli specyfikacją określającą format zapytań i odpowiedzi. Dzięki nim można upewnić się, że nowe wersje aplikacji nie wprowadzają zmian łamiących ustalone zasady komunikacji między systemami.

    2. Testy jednostkowe (Unit Testing)

    Testy jednostkowe API koncentrują się na pojedynczych endpointach. Ich celem jest sprawdzenie, czy endpoint zwraca poprawne odpowiedzi dla określonych danych wejściowych oraz czy prawidłowo obsługuje błędne lub niekompletne żądania.

    3. Testy end-to-end (E2E Testing)

    Testy end-to-end (E2E) sprawdzają kompletny przepływ działania aplikacji z wykorzystaniem API - od rozpoczęcia procesu aż do uzyskania końcowego rezultatu. Odwzorowują rzeczywiste działania użytkownika, aby potwierdzić poprawną współpracę wszystkich elementów systemu. Testy te obejmują wykonywanie serii powiązanych operacji i weryfikację, czy cały scenariusz biznesowy przebiega prawidłowo. Mogą wykorzystywać wiele endpointów oraz różnych interfejsów API.

    4. Testy obciążeniowe (Load Testing)

    Testy obciążeniowe służą do sprawdzenia, jak API zachowuje się przy dużej liczbie zapytań. Pozwalają ocenić wydajność systemu, czas odpowiedzi oraz stabilność działania pod wysokim obciążeniem.

    5. Testy bezpieczeństwa (Security Testing)

    Testy bezpieczeństwa mają na celu wykrywanie podatności i zagrożeń związanych z API. Obejmują m.in. sprawdzanie ochrony przed nieautoryzowanym dostępem, atakami typu injection czy wyciekami danych.

    6. Testy integracyjne (Integration Testing)

    Testy integracyjne sprawdzają współpracę API z innymi komponentami systemu. Ich zadaniem jest potwierdzenie poprawnej wymiany danych i komunikacji pomiędzy usługami lub modułami aplikacji.

    7. Testy funkcjonalne (Functional Testing)

    Testy funkcjonalne weryfikują, czy API realizuje wymagania biznesowe i działa zgodnie ze specyfikacją. Polegają na wysyłaniu określonych żądań oraz porównywaniu rzeczywistych wyników z oczekiwanymi rezultatami.

    5.2. Typowe błędy znajdowane podczas testowania API¶

    • Nieprawidłowy format danych - API może zwracać dane w niepoprawnym formacie lub zawierać błędne wartości. Problemy mogą dotyczyć:
      • niepoprawnej struktury JSON lub XML,
      • innego oczekiwanego formatu np. JSON zamiast XML,
      • brakujących pól,
      • błędnych typów danych,
      • niepoprawnych wartości.
    • Nieprawidłowe kody odpowiedzi HTTP - API może zwracać niewłaściwe statusy HTTP, które nie odpowiadają rzeczywistemu rezultatowi operacji. Przykładowo:
      • 200 OK mimo wystąpienia błędu,
      • 500 Internal Server Error przy błędzie walidacji danych,
      • brak 404 Not Found dla nieistniejącego zasobu.
    • Problemy z autoryzacją i uwierzytelnianiem - Błędy związane z bezpieczeństwem API należą do najczęstszych i najgroźniejszych problemów. Problemy mogą obejmować:
      • brak wymaganej autoryzacji,
      • możliwość dostępu bez tokena,
      • wygasłe lub niepoprawnie obsługiwane tokeny,
      • niewłaściwe uprawnienia użytkowników.
    • Brak walidacji danych wejściowych - API powinno poprawnie walidować dane przesyłane przez użytkownika. Brak odpowiedniej walidacji może prowadzić do błędów aplikacji lub luk bezpieczeństwa. Przykładowo:
      • możliwość przesłania pustych wartości,
      • akceptowanie zbyt długich danych,
      • brak sprawdzania wymaganych pól,
      • możliwość wykonania SQL Injection.
    • Problemy z wydajnością - API może działać poprawnie funkcjonalnie, ale nie radzić sobie pod większym obciążeniem. Przykładowo:
      • długi czas odpowiedzi,
      • timeouty,
      • przeciążenie serwera,
      • spadek wydajności przy wielu użytkownikach.
    • Problemy ze skalowalnością - Niektóre API działają poprawnie przy małej liczbie żądań, ale tracą stabilność przy większym ruchu. Może to prowadzić do:
      • błędów serwera,
      • utraty danych,
      • niedostępności usługi.
    • Problemy z dokumentacją API - Nieaktualna lub niekompletna dokumentacja API może utrudniać integrację oraz testowanie systemu. Najczęstsze problemy:
      • brak opisanych endpointów,
      • nieaktualne przykłady requestów,
      • brak informacji o parametrach,
      • niespójność dokumentacji z rzeczywistym działaniem API.
    • Problemy z kompatybilnością wersji API - Zmiany w nowych wersjach API mogą powodować problemy z działaniem istniejących aplikacji lub integracji korzystających ze starszych wersji interfejsu. Może to prowadzić do:
      • błędów integracji,
      • problemów z kompatybilnością,
      • uszkodzenia funkcjonalności aplikacji.
    • Luki bezpieczeństwa - Testowanie API pomaga wykrywać podatności bezpieczeństwa mogące prowadzić do wycieku danych lub nieautoryzowanego dostępu do systemu. Najczęstsze zagrożenia:
      • SQL Injection,
      • Cross-Site Scripting (XSS),
      • brak szyfrowania danych,
      • ujawnianie wrażliwych informacji,
      • brak limitowania liczby żądań.
    • Niepoprawna konfiguracja CORS - Błędna konfiguracja mechanizmu CORS może powodować problemy z komunikacją pomiędzy frontendem a API. Może to skutkować:
      • blokowaniem żądań między domenami,
      • problemami bezpieczeństwa,
      • błędnym działaniem aplikacji frontendowej.
    • Problemy ze współbieżnością - W przypadku wielu jednoczesnych żądań mogą pojawić się problemy związane z równoczesnym dostępem do danych. Najczęstsze problemy:
      • nadpisywanie danych,
      • duplikacja rekordów,
      • race conditions,
      • nieprzewidywalne działanie aplikacji.
    • Problemy z integracją systemów - API często komunikuje się z innymi aplikacjami, usługami lub bazami danych. Problemy integracyjne mogą powodować:
      • niespójność danych,
      • błędne działanie procesów biznesowych,
      • problemy z komunikacją między systemami.

    5.3. Wyzwania w testowaniu interfejsów API¶

    • Często brakuje interfejsu użytkownika (testowanie na poziomie żądań i odpowiedzi)
    • Walidacja danych i formatów
    • Obsługa autoryzacji i uwierzytelnienia

    5.4. Najlepsze praktyki testowania API¶

    • Utworzenie dedykowanego środowiska testowego - testy należy przeprowadzać na dedykowanym środowisku testowym (odzwierciedlającym warunki produkcyjne i zawierajacym dane pozorowane) przed wdrożeniem zmian na środowisku produkcyjnym
    • Automatyzacja testów - dzięki niej można ograniczyć występowanie błędu ludzkiego oraz możliwe jest wyliczenie pokrycia
    • Wykonywanie testów przez cały cykl życia API - pozwala identyfikować i rozwiązywać problemy tak szybko jak jest to możliwe.
    • Tworzenie testów wielokrotnego użytku - pomimo, że kazdy endpoint powinien być testowany indywidulanie, to mogąistnieć uniwersalne regóły np.
      • Każda odpowiedź na żądanie musi być w określonym czasie,
      • wszystkie odpowiedzi w formacie JSON
    • Odpowiednia organizacja testów - oznaczanie testów zgodnie z przeznaczeniem i ich grupowanie. Oddzielne zestawy testów dla każdego zasobu API i odzielnie testy jednostkowe od testów kompleksowych. Pomaga to uniknąć duplikowania testów.
